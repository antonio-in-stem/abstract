Java integration

Sealed data, typed access, honest security.

Compile once, seal the result into a .abx bundle, and load it in any JVM from Java 8 up. The authored data never sits as plain text inside your jar, and every modification is detected at load time.

The pipeline

.abt + .ab  ──>  abstract bundle --key "release passphrase"  ──>  data.abx
                                                                    │
             AbstractBundle.loadResource(Plugin.class, "/data.abx", key)
                                                                    │
                                                        AbstractData (typed API)

The bundle payload is the compiled JSON document encrypted with ChaCha20-Poly1305 (RFC 8439). The 22-byte header (magic, flags, format, nonce, length) is authenticated as associated data, so header tampering, truncation, and encryption-flag downgrades all fail with a clear error.

Create a bundle

abstract bundle path/to/project --key "my release passphrase" --out stickers.abx
abstract bundle path/to/project --key hex:8081...9f9f --out stickers.abx
abstract unbundle stickers.abx --key "my release passphrase"   # inspect
abstract bundle path/to/project --plain --out debug.abx        # unencrypted, debugging only

Passphrases are derived with SHA-256; hex: keys are used verbatim (64 hex digits). Re-bundling identical data still produces fresh ciphertext (per-seal nonces).

Load it in Java

The runtime lives in java/ in the repository: seven small files, zero dependencies, Java 8 compatible. Copy the package into your project or install it with Maven.

byte[] key = AbstractKeys.combine(KeyA.PART, KeyB.PART, KeyC.PART);
AbstractData data = AbstractBundle.loadResource(MyPlugin.class, "/data/stickers.abx", key);

for (AbstractObject sticker : data.byTemplate("Sticker")) {
    String rarity  = sticker.getString("rarity");
    long variants  = sticker.getInt("variant_count", 0);
    boolean shiny  = sticker.getBool("featured", false);
    String mode    = sticker.getString("slots.1.mode", "generate");

    for (AbstractObject entry : sticker.getObjects("lang_values")) {
        register(entry.getString("key"), entry.getString("value"));
    }
}

Paths are dotted ("stats.power", "slots.1.mode") and match the compiled JSON exactly.

Key handling that survives a decompiler

Never store the passphrase or the final key as one constant. Split it into XOR shares at build time and keep each share in a different class; ProGuard renaming then buries them in anonymous classes.

// Build time: run once, paste the printed arrays into separate classes.
byte[] key = AbstractKeys.fromPassphrase("my release passphrase");
for (byte[] share : AbstractKeys.split(key, 3)) {
    System.out.println(AbstractKeys.toJavaInitializer(share));
}

// Runtime: any single share reveals nothing.
byte[] key = AbstractKeys.combine(KeyA.PART, KeyB.PART, KeyC.PART);

The repository ships a ready proguard-rules.pro: it keeps the runtime API callable, renames everything else, enables aggressive optimization passes, and strips debug attributes. For string encryption and control-flow obfuscation on top, layer a commercial obfuscator (DexGuard, Zelix, Allatori).

The honest threat model

Read this before relying on bundles. Sealed bundles give you:

  • Confidentiality at rest: unzipping the jar or running strings reveals nothing.
  • Tamper evidence: a single flipped bit fails authentication loudly.
  • Downgrade resistance: a loader holding a key refuses plain bundles, so stripping the encryption flag does not work.

They cannot give you:

  • Protection from full reverse engineering. The key ships with the application; a determined attacker with a debugger will eventually recover it. Obfuscation raises the cost from minutes to days. It does not make it infinite. No client-side system does.
  • Licensing. Per-customer gating belongs on a server you control.

Design rule: bundle data you would be annoyed to see extracted, not data that would be catastrophic. Catastrophic data belongs on a server. For online applications, fetch one XOR share from your backend at startup so the jar alone cannot decrypt anything offline.

Verified interop

Both sides implement the same RFC 8439 vectors in their test suites: cargo test runs them in Rust, the JUnit suite and the dependency-free Selftest runner replay them in Java, and the cross-language fixture is a real bundle produced by the CLI (including non-ASCII content). If a JVM can run your application, it can open your bundles.

cd java
javac -d out $(find src -name '*.java')
java -cp out com.abstractlang.runtime.Selftest my-bundle.abx "my passphrase"
# selftest: all RFC 8439 vectors and unit checks passed
# selftest: opened bundle with 41 instance(s)

Full hardening checklist: java/SECURITY.md in the repository.
