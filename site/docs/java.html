Java integration

Sealed data, typed access, honest security.

Compile once, seal the result into a .abx container, and load it in any JVM from Java 8 up. The authored data never sits as plain text inside your jar, and every modification is detected at load time.

Bundles, the Java runtime and the editor extension are optional tooling. They ship with the reference implementation, operate on an already-compiled document, and never change compilation semantics. A conforming Abstract implementation is not required to provide any of them.

The pipeline

.abt + .ab  -->  abstract compile  -->  JSON document
                 abstract bundle --key "release passphrase"  -->  data.abx
                                                                    |
             AbstractBundle.loadResource(Plugin.class, "/data.abx", key)
                                                                    |
                                                        AbstractData (typed API)

The bundle payload is the compiled JSON document encrypted with ChaCha20-Poly1305 (RFC 8439). The 22-byte header (magic, flags, format, nonce, length) is authenticated as associated data, so header tampering, truncation and encryption-flag downgrades all fail with a clear error.

Create a bundle

abstract bundle m-project --key "my release passphrase" --out data.abx
abstract bundle m-project --key hex:8081...9f9f --out data.abx
abstract unbundle data.abx --key "my release passphrase"   # inspect
abstract bundle m-project --plain --out debug.abx          # unencrypted, debugging only

Passphrases are derived with SHA-256; a hex: key is used verbatim (64 hex digits). A bare 64-character hexadecimal string is a passphrase: only the hex: prefix selects raw key bytes, and the Java runtime derives keys by the same rule. Re-bundling identical data still produces fresh ciphertext, because every seal gets its own nonce.

RefusedWhy
--key together with --plaina supplied key must never be silently discarded, and no command may write an unencrypted container while a key was given
a flag value beginning with -bundle m-project --key --out x.abx is a usage error, not a container sealed with the passphrase --out
--key against a container that declares itself unencryptedthe refusal must not depend on caller behaviour
opening a container whose encryption flag was clearedfails whether or not the caller supplied a key

unbundle without a key on an unencrypted container is supported.

Load it in Java

The runtime lives in java/ in the repository: a handful of small files, zero dependencies, Java 8 compatible. Copy the package into your project or install it with Maven.

byte[] key = AbstractKeys.combine(KeyA.PART, KeyB.PART, KeyC.PART);
AbstractData data = AbstractBundle.loadResource(MyApp.class, "/data/stickers.abx", key);

for (AbstractObject sticker : data.byTemplate("Sticker")) {
    String rarity = sticker.getString("rarity");
    boolean glow  = sticker.getBool("glow", false);
    String team   = sticker.getString("owner.team", "unknown");

    for (AbstractObject entry : sticker.getObjects("copy")) {
        register(entry.getString("key"), entry.getString("value"));
    }
}

Paths are dotted ("owner.team", "slots.1.mode") and match the compiled JSON exactly. Because there is no null, has(path) is the only absence test you need.

Reading an older version

A compiled document carries the newest version in data and every earlier difference in overlays. forVersion(int) applies every overlay whose range contains the requested version, exactly as the specification prescribes: replace or add by id from the overlay’s data, then delete the ids in its removed.

AbstractData v1 = data.forVersion(1);

It must not assume that at most one overlay matches a version, and must not assume that every id in an overlay is already present in the base — an overlay may add an object the base does not carry at all.

Key handling that survives a decompiler

Never store the passphrase or the final key as one constant. Split it into XOR shares at build time and keep each share in a different class; ProGuard renaming then buries them in anonymous classes.

// Build time: run once, paste the printed arrays into separate classes.
byte[] key = AbstractKeys.fromPassphrase("my release passphrase");
for (byte[] share : AbstractKeys.split(key, 3)) {
    System.out.println(AbstractKeys.toJavaInitializer(share));
}

// Runtime: any single share reveals nothing.
byte[] key = AbstractKeys.combine(KeyA.PART, KeyB.PART, KeyC.PART);

The repository ships a ready proguard-rules.pro: it keeps the runtime API callable, renames everything else, enables aggressive optimisation passes and strips debug attributes. For string encryption and control-flow obfuscation on top, layer a commercial obfuscator.

The honest threat model

Read this before relying on bundles. Sealed bundles give you:

  • Confidentiality at rest. Unzipping the jar or running strings reveals nothing.
  • Tamper evidence. A single flipped bit fails authentication loudly.
  • Downgrade resistance. A loader holding a key refuses plain bundles, so stripping the encryption flag does not work.

They cannot give you:

  • Protection from full reverse engineering. The key ships with the application; a determined attacker with a debugger will eventually recover it. Obfuscation raises the cost from minutes to days. It does not make it infinite. No client-side system does.
  • Licensing. Per-customer gating belongs on a server you control.

Design rule: bundle data you would be annoyed to see extracted, not data that would be catastrophic. Catastrophic data belongs on a server. For online applications, fetch one XOR share from your backend at startup so the jar alone cannot decrypt anything offline.

Robustness requirements

The runtime is held to the same “never crash on input” rule as the compiler. Its JSON reader enforces a nesting-depth limit and reports it as the runtime’s own exception type rather than StackOverflowError; it rejects a leading +, leading zeros, duplicate object keys and lone surrogates; every parsing failure, including a malformed \u escape, surfaces as the runtime’s own exception type; and fromHex(null) or a non-hexadecimal digit never escapes as NullPointerException or NumberFormatException.

Verified interop

Both sides implement the same RFC 8439 vectors in their test suites: cargo test runs them in Rust, and the JUnit suite plus a dependency-free Selftest runner replay them in Java against a real bundle produced by the CLI, including non-ASCII content.

cd java
javac -d out $(find src -name '*.java')
java -cp out com.abstractlang.runtime.Selftest my-bundle.abx "my passphrase"

Full hardening checklist: java/SECURITY.md in the repository.
