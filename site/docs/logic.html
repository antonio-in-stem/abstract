Logic blocks turn schemas into policy.

Why logic exists

Schemas catch structural mistakes. Logic catches business mistakes: a public object may require an owner, a premium tier may require a support contact, or one derived field may depend on which child fields exist.

The philosophy is deliberately narrow. Logic derives values and validates relationships inside the template. That keeps domain policy close to the schema instead of hiding it in the compiler.

Basic rule

logic Product {
    derive .shipping_class = standard

    if .status == "active" {
        require .owner.contact exists
            else throw "Active products need an owner contact."
    }
}

The compiler validates the schema first, then evaluates the logic block bound to the instance template. A derive statement writes a computed value onto the current instance. If a require condition is false, compilation fails with the throw message.

Branches

logic Card {
    if .kind == "big" {
        derive .size = large
    } else if .kind == "medium" {
        derive .size = mid
    } else {
        derive .size = small
    }
}

if chains support else if and else. Both close-brace styles parse: } on its own line followed by else {, or the compact } else {.

Derivations

logic Card {
    derive .size = small          // always writes

    derive? .wave = 1             // writes only when the instance did not set it

    if .parts.2 exists {
        derive .size = large
    }
}

Use derive when a field is a consequence of other fields; the value is validated against the schema after logic runs. derive? respects authored values: it fills the field only when it is missing, which is the clean way to express "default that the author may override".

Derive values interpolate variables. A value that is exactly one variable keeps its native type; mixed text becomes a string:

for $n in [3] {
    derive .slot_count = $n                    // stays an int
    derive .banner = "pack $id uses $n slots"  // interpolated text
}

Loops

logic Page {
    for entry in .lang {
        require entry.value exists
            else throw "Every language entry needs a value."
    }

    for $slot in [1, 2] {
        if .slots.$slot.mode == "custom" {
            require .slots.$slot.distribution exists
                else throw "slot $slot needs distribution"
        }
    }
}

A for loop iterates over an array path or a literal list. Plain variables such as entry read object fields with paths like entry.value. Dollar variables such as $slot can be used inside dynamic paths and throw messages.

Path projection

Paths can project through arrays. If .applicable is an array of objects, then .applicable.id == "helmet" is true when any entry has that id.

Boundaries

  • Rules should read like policy, not like general-purpose code.
  • Diagnostics should point to the field that made the rule fail.
  • Derived values should be obvious from nearby schema fields.
  • Validation should still fail loudly when a relationship is impossible.

Use schema fields for shape and type. Use logic when the rule depends on relationships between fields.
