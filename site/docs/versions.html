Versions

One project, every release.

Abstract does not fork a project per release. It compiles every version in the declared range and expresses the older ones as overlays over the newest.

One project, several releases

A project declares its version range once, in any .abt file. A second declaration is E601; when there is none, the range is 1..1.

versions 1..3

Every version in the range is compiled. The compiled document carries the maximum version in data and every earlier difference in overlays.

Three places an annotation may go

ConstructWrittenScope
a fieldglow: bool @since(2) = falsethe field exists in versions 2 and up
a body statementglow: true   @since(2)the statement applies to versions 2 and up
an instance headerItem :: @id.lantern @since(2)the whole instance exists in versions 2 and up

@since(n) means v >= n; @removed(n) means v < n; both may appear, in either order, each at most once. n must be inside the project range (E603) and @removed must be strictly greater than the effective @since (E604).

Anywhere else — on a header tag, a clone statement or a body block — an annotation is E437. A version-scoped assignment goes in the body.

@since(2) with parentheses is an annotation. @since.2 is a header tag assigning 2 to a field named since, and a bare @since is a boolean flag on such a field. The parser decides on that one character and never looks further.

When a statement needs an annotation

versions 1..3

schema Item {
    name: text(1..40)
    glow: bool @since(2) = false
    legacy_tint: int(0..255) @removed(3) @optional
}
Item :: @id.torch
    name: Torch
    legacy_tint: 200

The assignment to legacy_tint carries no annotation, and needs none: a statement’s applicability set is intersected with the existence set of the field it writes, so it applies to versions 1 and 2 automatically. An annotation is needed only to give one field different values in different versions, or to narrow a statement further than the field’s own set:

Item :: @id.beacon
    name: Beacon
    legacy_tint: 200   @removed(2)
    legacy_tint: 250   @since(2)

That project is docs/examples/version-statements. Two statements writing one path must have disjoint applicability sets; overlapping ones are E429. A statement whose set is empty because it contradicts its field is E430; one that contradicts its own instance’s window is E440.

Every version must compile

An instance is compiled once for every version in its window, and every check — required fields, ranges, cardinality, require — runs in each. A required field must have a value in every version in which it exists; annotating the only statement that supplies it is E411 in the versions the annotation excludes.

Logic that reads a version-scoped field must guard it, because an operand resolving to no value makes every comparison false:

if .glow exists {
    require .glow == false else throw "glow must start off."
}

Logic that writes one must guard it too, because a derive executing against a field that does not exist in the version being compiled is E521:

if version < 3 {
    derive? .legacy_tint = 0
}

A field is never removed and re-added: its existence set is always one contiguous interval. To express “present, then absent, then present”, declare two differently named fields, or keep the field declared throughout and control its value with two annotated statements. Assets are not versioned: a project that needs different bytes for different releases keeps them in separate directories and chooses between them outside Abstract.

Instance windows

This is docs/examples/instance-windows, with the schema above.

Item :: @id.lantern @since(2)
    name: Lantern

Item :: @id.candle @removed(3)
    name: Candle

In a version outside its window an instance simply does not exist: it contributes no object, it is not validated, and its require statements do not run. Ids remain unique project-wide even when two windows are disjoint — a window narrows when an instance exists, never who owns its id. To replace one object with another across a version boundary, give the two instances different ids and let the overlay’s removed list retire the first.

A clone source must exist wherever the cloning instance does (E440), and a ref value must name an instance that exists in the version being compiled (E431).

What comes out

The base is version 3, which carries lantern and not candle:

{
  "abstract": {
    "format": 1,
    "compiler": "1.0.0",
    "versions": { "min": 1, "max": 3 }
  },
  "data": [
    { "template": "Item", "id": "lantern", "name": "Lantern", "glow": false }
  ],
  "overlays": [
    {
      "versions": { "min": 1, "max": 1 },
      "data": [ { "template": "Item", "id": "candle", "name": "Candle" } ],
      "removed": [ "lantern" ]
    },
    {
      "versions": { "min": 2, "max": 2 },
      "data": [ { "template": "Item", "id": "candle", "name": "Candle", "glow": false } ],
      "removed": []
    }
  ]
}

Read it entry by entry. lantern’s version-2 object is identical to the base’s, so that run is discarded; its only entry is a removal over 1..1, where it does not exist. candle has no base object at all, and its two objects differ because glow exists only from version 2, so it contributes two replace entries. Grouping by range gives the two overlays above.

The exact byte layout of the document is shown compactly here; the stored expectation is in docs/examples/instance-windows/expected.json.

How a consumer reads a version

  1. Start from data.
  2. Apply every overlay whose range contains the version: replace or add each object in its data by id, then delete every id in its removed.

There may be no matching overlay, one, or several. Nothing is merged and no field is deleted individually, so a lookup by id is all a consumer needs. The ranges of two overlays may overlap, but for any single id the ranges that mention it are disjoint, so no id is touched twice and the order does not matter.

Overlay entries are whole objects. There is no field-level delta and no null: a field that does not exist in a version, or that has no value there, is simply absent from that version’s object.

Full contract, including structural equality and the grouping rules: compiled data.
