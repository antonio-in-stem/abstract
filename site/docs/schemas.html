Schema authoring

Describe the shape once.

A schema declares what valid data looks like — and, because the declared order of fields is the output key order, what it looks like on the way out.

Shape of a declaration

schema <Name> {
    <name>[ "[" [cardinality] "]" ] : <type> [modifiers] [= default]

    <name>[ "[" [cardinality] "]" ] [modifiers] {
        <fields>
    }
}

A schema name starts with an ASCII letter and continues with letters, digits and _. Names are compared exactly and must be unique across the whole project (E301). Field names are identifiers and are normalised, so two fields in one block that differ only in case or in - versus _ are E302.

The declared order of fields is the key order of the compiled output. A schema is a layout as well as a contract.

Modifiers

ModifierMeaning
[]The field is a list. Optionally carries a cardinality: [1..], [2..4].
@optionalThe field may be absent, and is then omitted from the output.
@tagInside a group: the field that receives #value shorthand.
@since(n) / @removed(n)The field exists only in some versions.
= valueA default, filled before logic runs.

Each modifier may appear at most once per field (E303), and every modifier comes after the type and before the =:

glow: bool @since(2) = false      // correct
glow: bool = false @since(2)      // E303

Required, optional, defaulted

DeclarationWhen absent
title: text(1..60)E411 — required
tier: enum(free, plus) = freefilled with free before logic runs
slot_count: int(1..9) @optionalomitted from the output
notes[]: text @optionalomitted — not []

A field must not carry both @optional and a default (E320): the default would make it always present. A default is validated against its own type at schema-validation time (E313), not lazily when some instance happens to omit the field, and it is interpolated at the moment it is filled in, against that instance’s variables.

Lists and cardinality

HeadMeaning
tags[]any number of elements, including none
tags[2..]at least 2
tags[2..4]between 2 and 4
tags[3], tags[..4], tags[4..2]E323
tags[][]E315 — nested lists do not exist

A value whose element count falls outside the cardinality is E445. Cardinality constrains a value, never presence: an absent optional list is omitted and is not E445. A required list with no cardinality is satisfied by an explicit tags: [].

Groups and list groups

This is docs/examples/groups-and-lists.

schema Product {
    title: text(1..60)
    owner {
        team: text(1..50)
        contact: text(1..80) @optional
    }
    tags[1..3]: enum(core, public, internal)
    capabilities[] {
        id: enum(search, sync, export) @tag
        availability: enum(alpha, beta, stable) = stable
    }
    notes[]: text @optional
}
Product :: @id.atlas
    title: Atlas Search
    owner {
        team: Knowledge Systems
    }
    tags: core, public
    capabilities: [#search, #export(availability: alpha)]
{
  "template": "Product",
  "id": "atlas",
  "title": "Atlas Search",
  "owner": { "team": "Knowledge Systems" },
  "tags": ["core", "public"],
  "capabilities": [
    { "id": "search", "availability": "stable" },
    { "id": "export", "availability": "alpha" }
  ]
}

Both owner.contact and notes are optional and absent, so neither key appears. A group is present when something wrote a value at or under it; an absent optional group is omitted entirely and its children’s defaults are not filled, while an absent required group is E411.

Keyed lists: @tag

@tag marks the one field of a group that receives #value shorthand in instances.

RuleError when broken
must be on a field inside a group or list group, never at rootE311
at most one per groupE310
non-list text, int, bool or enum onlyE322
may carry a default or @optional, not bothE320

The tagged field need not be called id. With key: enum(en_us, es_es) @tag, the shorthand #es_es fills key and nothing named id ever appears. A list whose element group declares @tag is a keyed list: two elements sharing a key are E444, and clone merging folds such lists by key instead of replacing them.

Numbered keys

A field name may be all digits. This is docs/examples/numbered-keys.

schema Slot {
    mode: enum(fixed, free) = free
    capacity: int(0..64) @optional
}

schema Pack {
    title: text(1..40)
    slots {
        1: $(Slot)
        2: $(Slot) @optional
        3: $(Slot) @optional
    }
}
Pack :: @id.winter
    title: Winter
    slots.1.mode: fixed
    slots.1.capacity: 16
    slots.2.capacity: 8
"slots": {
  "1": { "mode": "fixed", "capacity": 16 },
  "2": { "mode": "free", "capacity": 8 }
}

A numbered key is an ordinary field name, not an array index: there is no index syntax in an assignment or clone path. In JSON and YAML it is a string key, so no consumer mistakes it for a number. Slot 2 is present because something was written under it, so its mode default was filled; slot 3 is absent and optional, so it is omitted.

The two reserved names

DeclarationVerdict
template: textE314 — always
id: textvalid: unconstrained
id: text(3..24)valid: constrains the instance id
id: int, id[]: text, id: text @optional, id: text = xE314

Every schema has an implicit id: text(1..64). Declaring it explicitly never changes what the id is and never changes the output — the id is emitted once, as the second key — it only constrains and documents it. Inside a group, both names are ordinary field names, because a nested object carries no envelope.

Recursion

A schema may refer to itself through $(Schema), provided every cycle passes through an @optional field or a list field. A cycle in which every edge is a required, non-list $(Schema) field is E321: no finite object satisfies it. Legal recursive structures are bounded at compile time by the document depth limit of 64 (E209).
